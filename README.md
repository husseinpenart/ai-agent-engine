# Local agent backend

The Tauri frontend connects to the ASP.NET API, for example at `https://localhost:44382` when using the IIS Express profile. The backend starts a private `llama-server` process on an available loopback port on the first chat request. This process reads the configured GGUF directly; the Ollama service and model import are not required. The executable and CUDA libraries currently come from the installed Ollama directory and can be changed in `appsettings.json`.

Start the backend with the IIS Express profile in Visual Studio, or run `dotnet run --no-launch-profile` and configure the frontend to use `http://localhost:5000`. In development, Swagger UI is available under `/swagger`. `GET /api/health` reports API availability; it does not load the model. `POST /api/agent/chat` streams SSE events and can take time on its first request while the model loads.

`appsettings.json` configures both GGUF model paths, the vision projector, CUDA backend directory, context sizes, CPU threads, GPU layers, output lengths and idle timeout. The coder uses an 8192-token context, 4096 output tokens and automatic GPU layer fitting with a target of 1024 MiB free VRAM. Vision uses 99 GPU layers and GPU projector offload, a 4096-token context and 1024 output tokens. Flash Attention is set to `auto` so the runtime chooses it when supported. Prompt batch/microbatch defaults are 1024/256 for coder and 512/128 for vision. These are starting points, not measured performance guarantees; tune them for available memory. Only one model process per backend instance runs at a time: an image request unloads the coder, analyzes images locally, unloads vision and starts the coder. Other applications or backend instances can still consume GPU and system memory. If the vision model cannot fit, the request reports an error; it does not silently switch its projector to CPU. The process stops after five idle minutes. `HttpClient` has no fixed timeout and requests remain cancellable by the client.

The API is intended for local use and has no authentication; do not expose it to a network. `POST /api/agent/chat` optionally accepts up to four `images` objects containing `id`, `name` and a PNG, JPEG or WebP base64 `dataUrl` (5 MB combined). The response emits `status` and `vision_report` events before the coding stream. Vision reports are untrusted observations, not guaranteed exact transcriptions. The client executes tools and manages permissions; desktop conversation storage is managed by the frontend. The default context keeps eight recent messages, preserves complete tool-call groups and truncates individual tool results to 1200 characters. Older turns are reduced to bounded extractive excerpts, not a lossless or model-generated summary. A tool group or the latest user request may add messages beyond that limit. Streaming length stops are reported to the client for continuation; interrupted streams are only continued when text has already arrived, and incomplete tool calls are never executed.

Files in the backend's `wwwroot`, when present, are served normally. To preview a separate public output directory, explicitly set `StaticFiles:PreviewDirectory` to its absolute path (or a path relative to the backend), restart the server, and open `/preview/index.html`. Only files suitable for public access should be placed there: the API has no authentication. The setting is empty by default and does not expose the agent's selected workspace automatically. The Tauri file tools replace completed writes atomically and retry temporary sharing violations; a program that denies file replacement can still cause a controlled error. Separate agent write/append calls can expose intermediate versions of a page.

Model ownership is serialized across agent backend instances in the same login session. On Windows each model process is attached to a kill-on-close job so that terminating IIS Express or Kestrel also terminates the model. The agent records its owned process PID, creation time, executable and port in `%LOCALAPPDATA%\my-agent\model-process.json` (configurable through `Model:ProcessStateDirectory`). On the next startup, it verifies those fields before terminating a surviving owned process. Unknown or pre-existing processes without an ownership record are not terminated automatically. Requests that fail or are cancelled stop the active model; successful requests keep it loaded until the idle timeout. Process starts and stops log the PID and port.
